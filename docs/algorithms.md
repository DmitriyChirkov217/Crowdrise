# Основные алгоритмы программы

Документ описывает основные алгоритмы backend-части приложения. Временная финансовая интеграция здесь не рассматривается, потому что она должна быть заменена полноценным подключением к внешнему банковскому или сервисному провайдеру.

Код алгоритмов в документ не вставляется полностью. Вместо этого для каждого алгоритма указан один основной фрагмент кода, который можно использовать как пример реализации. Номера строк актуальны для текущего состояния проекта.

## 1. Создание проекта автором

Создание проекта начинается с HTTP-запроса авторизованного пользователя с ролью `author`. На уровне обработчика запрос преобразуется в структуру входных данных, после чего управление передается сервисному слою. Сервис выполняет базовую валидацию полей проекта: проверяет название, описание, тип кампании, валюту, целевую сумму и даты. После этого репозиторий открывает транзакцию, создает запись проекта в таблице `projects` со статусом `draft`, а затем создает связанную строку в `project_funds`, где в дальнейшем будут храниться собранные, зарезервированные, доступные и возвращенные средства проекта. После фиксации транзакции проект повторно считывается из базы и возвращается вызывающему коду.

Пример кода алгоритма: `backend/internal/repositories/postgres.go`, строки 298-319.

Основные таблицы: `projects`, `project_funds`.

## 2. Редактирование проекта

Редактирование проекта доступно только автору проекта и только до публикации: проект должен находиться в статусе `draft` или `rejected`. Backend сначала получает текущую запись проекта из базы, затем сравнивает `author_id` проекта с идентификатором пользователя из JWT. Если пользователь не является автором, возвращается ошибка доступа. Если статус проекта уже не позволяет редактирование, возвращается ошибка некорректного статуса. При успешной проверке обновляются основные поля проекта: название, описание, категория, тип кампании, валюта, целевая сумма и даты.

Пример кода алгоритма: `backend/internal/repositories/postgres.go`, строки 321-342.

Основная таблица: `projects`.

## 3. Добавление этапа проекта

Этап проекта добавляется автором на стадии подготовки проекта. Backend проверяет существование проекта, принадлежность проекта текущему пользователю и статус проекта. Если проект уже отправлен на модерацию или опубликован, добавление этапов запрещено. При успешной проверке создается запись в таблице `milestones` со статусом `planned`. Для этапа сохраняются название, описание, дата выполнения, сумма этапа и позиция, по которой этапы затем сортируются.

Пример кода алгоритма: `backend/internal/repositories/postgres.go`, строки 360-379.

Основные таблицы: `projects`, `milestones`.

## 4. Добавление вознаграждения

Вознаграждение добавляется к проекту автором и используется для проектов типа `reward`. Перед созданием записи backend проверяет, что пользователь является автором проекта. Затем создается строка в таблице `rewards`, где хранятся название, описание, минимальная сумма поддержки, лимит количества и примерная дата доставки. Наличие хотя бы одного вознаграждения позже проверяется при отправке reward-проекта на модерацию.

Пример кода алгоритма: `backend/internal/repositories/postgres.go`, строки 474-493.

Основные таблицы: `projects`, `rewards`.

## 5. Отправка проекта на модерацию

Отправка проекта на модерацию переводит проект из черновика в состояние ожидания решения администратора. Backend открывает транзакцию и блокирует строку проекта на время проверки. Затем проверяется, что запрос сделал автор проекта, после чего система считает количество этапов, сумму всех этапов и количество вознаграждений. Доменное правило требует, чтобы проект находился в статусе `draft` или `rejected`, имел хотя бы один этап, сумма этапов совпадала с целевой суммой проекта, а для reward-проекта было создано хотя бы одно вознаграждение. Если все условия выполнены, статус проекта меняется на `on_review`.

Пример кода алгоритма: `backend/internal/repositories/postgres.go`, строки 535-575.

Основные таблицы: `projects`, `milestones`, `rewards`.

## 6. Решение администратора по проекту

После проверки проекта администратор может принять одно из трех решений: `approved`, `rejected` или `blocked`. Backend преобразует это решение в итоговый статус проекта: публикацию, отклонение или блокировку. Затем проект обновляется в таблице `projects`, а автору создается событие в `notification_outbox`. Если проект одобрен, он становится доступен в публичном каталоге как опубликованный; если отклонен, автор может исправить данные и снова отправить проект на модерацию.

Пример кода алгоритма: `backend/internal/repositories/postgres.go`, строки 577-596.

Основные таблицы: `projects`, `notification_outbox`.

## 7. Отправка отчета по этапу

Когда проект уже опубликован, автор может отправить отчет по отдельному этапу. Backend открывает транзакцию, получает этап вместе с проектом и блокирует строку этапа. Затем проверяется, что отчет отправляет автор проекта, проект находится в статусе `published`, а сам этап имеет допустимый статус: `planned`, `in_progress` или `rejected`. После этого создается запись в `milestone_submissions`, к ней добавляются файлы из `milestone_submission_files`, а статус этапа меняется на `on_review`. В конце создается событие уведомления о том, что отчет был отправлен.

Пример кода алгоритма: `backend/internal/repositories/postgres.go`, строки 815-860.

Основные таблицы: `milestones`, `projects`, `milestone_submissions`, `milestone_submission_files`, `notification_outbox`.

## 8. Проверка отчета по этапу администратором

Проверка отчета по этапу выполняется администратором после того, как автор отправил отчет. Backend открывает транзакцию, блокирует строку этапа и проверяет, что этап действительно находится в статусе `on_review`. Затем создается запись в `milestone_reviews`, фиксирующая решение администратора и комментарий. Если отчет одобрен, статус этапа меняется на `approved`, из `project_funds.total_reserved` вычитается сумма этапа, а в `project_funds.total_available` эта сумма добавляется. Также в `fund_ledger` создается операция `release`. Если отчет отклонен, статус этапа становится `rejected`, а средства остаются зарезервированными.

Пример кода алгоритма: `backend/internal/repositories/postgres.go`, строки 862-922.

Основные таблицы: `milestone_reviews`, `milestones`, `project_funds`, `fund_ledger`, `notification_outbox`.

## 9. Комнаты трансляций и документы

Комната трансляции создается автором проекта и хранится в таблице `broadcast`. Backend проверяет, что проект существует и что текущий пользователь является его автором. После этого создается комната со статусом `scheduled`, `live` или `ended`. Автор также может менять статус комнаты, удалять комнату и добавлять документы трансляции. Документы хранятся отдельно в `broadcast_chat_files` и связаны с комнатой через `broadcast_id`. При удалении комнаты документы удаляются каскадно за счет связи в базе данных.

Пример кода алгоритма: `backend/internal/repositories/postgres.go`, строки 1078-1185.

Основные таблицы: `broadcast`, `broadcast_chat_files`, `projects`.

## 10. Голосовой чат WebRTC mesh

Голосовой чат реализован по схеме WebRTC mesh. Backend не передает аудиопоток между пользователями, а выполняет роль signaling-сервера. При подключении пользователь передает JWT, backend проверяет токен, убеждается, что пользователь не заблокирован и что комната трансляции существует и не завершена. После успешной проверки WebSocket-подключение добавляется во внутреннюю in-memory комнату. Hub отправляет новому участнику список уже подключенных peers и пересылает между участниками сообщения `offer`, `answer`, `ice_candidate`, `mute` и `peer_left`. Участники голосового чата в базе данных не сохраняются.

Пример кода алгоритма: `backend/internal/realtime/hub.go`, строки 46-175.

Основные данные: `broadcast`, `users`, in-memory список WebSocket-подключений.

## 11. Публикация обновления проекта

Автор опубликованного проекта может добавить обновление, которое сохраняется в `project_updates`. Backend проверяет, что пользователь является автором проекта, создает запись обновления, затем находит всех спонсоров проекта с оплаченными поддержками и создает для них события в `notification_outbox`. Таким образом, обновление проекта не только сохраняется как публичная запись, но и становится основанием для уведомления заинтересованных пользователей.

Пример кода алгоритма: `backend/internal/repositories/postgres.go`, строки 924-963.

Основные таблицы: `project_updates`, `projects`, `pledges`, `notification_outbox`.
